**Parent architecture:** UNIVERSAL ENGINE / ENGINEER  
**Architecture:** NINEFOLD INTRINSIC — MULTIVERSAL OMNIVELOCITY PRIME (9 FOLD OMNI)  
**Governance:** NINEFOLD INTRINSIC — MULTIVERSAL OMNI GOVERNANCE PRIME  
**Intrinsic intelligence and continuity:** AFI OM × EB9 PRIME  
**Status:** Proposed evaluation plan. No framework is approved for production integration by this document.

## 1. Decision recorded

Evaluate the following nine external projects as capability references and potential implementation components:

1. LangChain / LangGraph
2. OpenAI Agents SDK
3. Google Agent Development Kit (ADK)
4. Microsoft Agent Framework
5. CrewAI
6. Claude Agent SDK
7. OpenHands
8. LlamaIndex
9. DSPy

The list is a deliberately selected benchmark set, not a universal ranking. These projects occupy different layers (application framework, runtime, harness, specialist engineering agent, retrieval framework and optimisation toolkit); they must not be treated as interchangeable products.

**Approval boundary:** Agreement to investigate and benchmark is not approval to install, integrate, execute, grant credentials to, or deploy every candidate. Selection follows evidence, compatibility, licensing, security, resource and acceptance review.

## 4. Nine evaluation dimensions

Every candidate is assessed against the same dimensions, with evidence and confidence recorded separately:

1. **Functional capability:** Does the candidate demonstrably perform the required function?
2. **Reliability and recovery:** State persistence, restart, timeout, retry, idempotency and failure isolation.
3. **Security and authority:** Identity, least privilege, tool permissions, sandboxing, secrets, egress and prompt-injection boundaries.
4. **Memory and continuity:** State model, durable storage, provenance, retrieval, conflict handling and exportability.
5. **Interoperability:** Model/provider neutrality, APIs, MCP/A2A where relevant, language support and integration contracts.
6. **Performance and resource use:** Latency, throughput, token/API cost, CPU, RAM, storage and mobile/cloud constraints.
7. **Observability and evidence:** Traces, logs, reproducibility, audit records, evaluation support and independent verification.
8. **Maintainability and supply chain:** Licence, dependency health, release cadence, compatibility, community/vendor risk and upgrade path.
9. **Evolution and optimisation:** Evaluation-driven improvement, versioning, regression detection, rollback and safe adaptation.

## 5. Benchmark protocol

### Phase A — Documentation and provenance
- Pin official documentation, repository, licence and release/version at evaluation time.
- Record source URL, retrieval date, version, supported platform and evidence excerpt.
- Separate documented features from independently tested behaviour and vendor claims.
- Identify preview, beta, deprecated and production-stability labels from first-party sources.

### Phase B — Common workload suite
Run equivalent tasks where the abstraction permits. Do not force a retrieval framework or optimisation toolkit into an agent-runtime test it was not designed to perform.

Required workload families:
- Tool selection and bounded tool execution.
- Multi-step task planning and deterministic workflow execution.
- Multi-agent delegation with preserved specialist findings.
- Human approval and denial paths.
- Process interruption, restart and state recovery.
- Timeout and ambiguous-outcome handling.
- Retrieval with source attribution and conflicting evidence.
- Repository issue analysis, code change, test execution and review.
- Adversarial prompt/tool input and permission-boundary tests.
- Evaluation-driven optimisation with held-out regression tests.

### Phase C — Measurement
For each run record:
- Exact framework and dependency versions.
- Model/provider and configuration.
- Hardware/runtime environment.
- Input fixture and task identifier.
- Start/end time, latency and completion outcome.
- Token/API cost and resource consumption where measurable.
- Tool calls, approvals, denials and side effects.
- Failure/recovery behaviour.
- Output quality rubric and independent assessor.
- Evidence digest and reproducibility information.

### Phase D — Independent review
- Use blinded assessment where feasible.
- Require an evaluator independent of the implementation under test.
- Preserve raw results under approved privacy and retention controls; digest-only ledgers alone are not a substitute for inspectable evidence.
- Record disagreements, failed trials and missing evidence.
- Never allow a candidate to certify its own correctness or security.

## 6. Scoring and selection

Use a 0–5 scale for each dimension:
- 0 = absent or failed
- 1 = weak / mostly manual
- 2 = partial / significant limitations
- 3 = adequate for a defined use case
- 4 = strong, repeatable evidence
- 5 = exceptional, independently reproduced evidence

A score must cite evidence. Unknown is **Not Assessed**, not zero and not a guessed score. Report per-dimension scores and confidence; do not hide critical weaknesses inside a single weighted average.

Hard gates before any integration:
- Licence and terms reviewed for intended use.
- Security and threat model reviewed.
- No unresolved critical permission or isolation defect.
- Resource budget and supported target environment established.
- Interface and data contracts versioned.
- Failure semantics and rollback defined.
- Tests pass in an isolated environment.
- Independent review completed.
- Explicit architecture-owner approval recorded.

## 7. Integration strategy — provisional, not a deployment decision

Initial candidates for deeper technical investigation:
- **LangGraph:** stateful orchestration and recoverable workflows.
- **OpenHands:** repository-level software engineering execution.
- **LlamaIndex:** knowledge ingestion and retrieval.
- **DSPy:** evaluation-driven optimisation.

Compare OpenAI Agents SDK, Google ADK, Microsoft Agent Framework, CrewAI and Claude Agent SDK as alternative or complementary implementations for specific interfaces and workloads.

Do not run multiple overlapping orchestration frameworks in production without a demonstrated need. Prefer one primary orchestration runtime with replaceable adapters and isolated specialist execution. A framework may be used as a test comparator without being adopted.

## 8. AFI OM × EB9 PRIME integration contract

All candidate integrations must use governed interfaces:
- AFI OM receives structured, provenance-bearing findings and performs synthesis under policy.
- EB9 PRIME manages approved memory acquisition, encoding, indexing, contextual recall, reconciliation and continuity.
- Memory writes require provenance, scope, retention and conflict handling.
- Framework state is not automatically canonical memory.
- Cross-UMIC sharing requires explicit scoped grants.
- Candidate agents cannot mutate governance registers or grant themselves authority.
- Evidence records must distinguish observed facts, model-generated hypotheses, simulations and predictions.

## 9. Initial acceptance criteria

The benchmark is complete only when:
- All nine candidates have a sourced capability profile or a documented reason a candidate cannot be evaluated.
- At least one representative workload is run for each applicable candidate.
- Comparable workloads are used for comparable abstractions.
- Results include failures, costs, resource use and confidence—not only successful demonstrations.
- Security, licence and operational risks are recorded.
- A shortlist is justified by evidence and target-environment fit.
- Rejected candidates and reasons remain in the register.
- No production integration is inferred from a documentation review or benchmark score alone.

## 10. Current status and limitations

This document establishes the evaluation plan only. It does not claim that the nine frameworks have been installed, benchmarked, integrated, security-audited or approved. No performance ranking is asserted. Implementation choices remain open pending reproducible tests on the intended runtime and target devices.

**Governing principle:** PROOF BEFORE CLAIM. EVIDENCE BEFORE CONFIDENCE. VERIFICATION BEFORE COMPLETION.
